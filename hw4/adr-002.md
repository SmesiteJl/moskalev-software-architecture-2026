# ADR-002. Резерв товара условным UPDATE, каталог читает остаток из кэша

Статус: принято. Версия: v1, 30.09.2026

## Контекст

К остатку товара два требования, и они противоречат друг другу:

- QS-02: если 200 человек одновременно берут последнюю единицу, пройти должен ровно один заказ;
- QS-01: каталог показывает остатки и отвечает за 300 мс при 1 000 запросов в секунду.

Если каталог будет читать остаток из той же таблицы, по которой идут резервы, вся нагрузка каталога придётся на основную базу. Если читать из кэша, покупатель иногда увидит товар, который только что закончился.

## Варианты

Как защитить остаток при резерве:

| Вариант | Как работает | Недостаток |
|---|---|---|
| A. `SELECT ... FOR UPDATE` | Блокируем строку, проверяем в коде, обновляем | Два запроса вместо одного. Правило находится в коде, а не в базе |
| **B. Условный `UPDATE`** | `UPDATE ... WHERE on_hand - reserved >= :qty`, смотрим, сколько строк обновилось | Популярный товар: запросы к одной строке выстраиваются в очередь |
| C. Версия строки | Читаем версию, обновляем, если она не изменилась, иначе повторяем | При 200 одновременных запросах — лавина повторов |
| D. Счётчик в Redis | Уменьшаем счётчик в Redis, в базу пишем потом | Два источника истины. Заказ и резерв уже не одна транзакция |

Откуда каталог берёт остаток:

| Вариант | Недостаток |
|---|---|
| Из основной базы | 1 000 запросов в секунду на базу, которая принимает заказы |
| **Из Redis, который обновляется событиями `StockChanged`** | Остаток отстаёт на время доставки события |

## Решение

Резерв — вариант B: условный `UPDATE` по каждой позиции в той же транзакции, что и заказ. Обновилось 0 строк хотя бы по одной позиции — откатываем всё и отвечаем `409 OUT_OF_STOCK`. Дополнительно в таблице стоит `CHECK (reserved <= on_hand)`.

Каталог читает остаток из Redis. После каждого изменения остатка Order Core пишет событие `StockChanged`, Catalog Service обновляет кэш. Раз в 5 минут кэш остатков целиком пересобирается из read replica — на случай, если событие потерялось.

Решение о резерве принимает только PostgreSQL. Кэш в нём не участвует.

## Последствия

Плюсы:

- QS-02 выполняется средствами одной базы: первый запрос блокирует строку и проходит, остальные после него видят, что товара уже нет, и получают `409`;
- даже если в коде ошибка, `CHECK` не позволит зарезервировать больше, чем есть;
- каталог не нагружает основную базу.

Минусы:

- покупатель может положить в корзину товар, который закончился несколько секунд назад, и получить отказ при оформлении. Приложение должно показать, чего именно не хватает;
- очередь на популярный товар. Блокировка строки держится до конца транзакции, это 5–15 мс. 30 одновременных резервов одного товара ждут до 0,5 с — это допустимо. Если будут акции, где один товар берут сотни человек сразу, решение придётся менять.

## Проверка

- CONC-01: 200 запросов на остаток 1 — один `201`, 199 `409`, `reserved = 1`;
- доля отказов `OUT_OF_STOCK` при оформлении не выше 1%. Если выше — кэш отстаёт слишком сильно;
- ежечасная сверка в базе: строк с `reserved > on_hand` нет.
