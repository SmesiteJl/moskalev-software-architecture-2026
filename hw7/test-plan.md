# Test Plan и Traceability: eat-easy

Версия: v1, 30.09.2026. Требования — из [SRS](../hw2/srs.md), решения — из [ДЗ 4](../hw4/hld.md).

## 1. Три требования

Взял три требования разного типа, чтобы понадобились разные виды тестов. Одним видом всё не проверить: API-тест не покажет p95, а нагрузочный не найдёт гонку.

| ID | Требование | Почему оно |
|---|---|---|
| FR-03 | Заказ создаётся вместе с резервом товара: всё или ничего | Главная функция системы |
| NFR-01 | `GET /catalog`: p95 ≤ 300 мс при 1 000 rps | Ради него каталог вынесен в отдельный сервис. Оправдано это или нет, покажет только замер |
| NFR-03 | Резерв не больше остатка, нет дублей заказа и платежа, один курьер на заказ | Главный риск системы — гонки |

## 3. Тесты для FR-03

Где запускаем: Order Core, PostgreSQL и RabbitMQ в контейнерах, вместо PSP заглушка.

**IT-03. Заказ создаётся**

- Дано: покупатель вошёл, адрес в зоне. Товар А: остаток 10, резерв 0. Товар Б: остаток 5, резерв 1.
- Шаги: `POST /orders` — товар А × 2, товар Б × 1.
- Expected result: `201`, статус `AWAITING_PAYMENT`. В базе один заказ и две позиции. Резерв товара А стал 2, товара Б — 2. В outbox есть событие `PaymentRequested`.
- Evidence: отчёт теста, значения `reserved` до и после.

**IT-04. Товара не хватает**

- Дано: то же, плюс товар В: остаток 1, резерв 1.
- Шаги: `POST /orders` — товары А, Б и В.
- Expected result: `409 OUT_OF_STOCK`, в ответе указан товар В. Заказ не создан. Резерв товаров А и Б не изменился.
- Evidence: отчёт теста, число строк в `orders` до и после.

В этом же тесте проверяются остальные отказы: пустая корзина — `400`, нет токена — `401`, адрес вне зоны — `422`.

**E2E-01. Весь путь заказа**

- Дано: развёрнут весь стенд, на смене есть тестовый курьер.
- Шаги: покупатель оформляет заказ → тестовый PSP подтверждает холд → курьер принимает оффер → сборщик собирает → курьер забирает и доставляет.
- Expected result: заказ проходит `AWAITING_PAYMENT → PAID → PICKING → READY → IN_DELIVERY → DELIVERED`. У PSP один холд и одно списание. Резерв вернулся к исходному, остаток уменьшился на собранное.
- Evidence: история статусов заказа, журнал тестового PSP.

## 4. Тест для NFR-01

**PERF-01. Каталог под пиковой нагрузкой**

| | |
|---|---|
| Стенд | Как production: 3 инстанса Catalog Service, Redis, read replica |
| Данные | 30 дарксторов по 3 000 товаров |
| Нагрузка | Разгон 5 минут, потом 30 минут ровно 1 000 запросов `GET /catalog` в секунду. Параллельно 10 заказов в секунду, чтобы остатки менялись |
| Инструмент | Gatling, метрики в Prometheus |
| Где измеряем | На API Gateway |
| Expected result | p95 ≤ 300 мс, p99 ≤ 700 мс, ошибок не больше 0,1% |
| Evidence | Отчёт Gatling, снимок дашборда за время теста, версия сборки |

Дополнительный прогон: Redis отключён на 5 минут при той же нагрузке. Expected result: ни один инстанс каталога не перезапустился, каталог отвечает за p95 ≤ 1 с и даёт не больше 1% ошибок, оформление заказов остаётся в пределах NFR-02.

## 5. Тесты для NFR-03

Тест с одним клиентом гонку не воспроизводит. Здесь запросы стартуют одновременно и распределяются по 3 инстансам Order Core.

**CONC-01. Последняя единица товара**

- Дано: товар X, остаток 1, резерв 0. 200 покупателей.
- Шаги: 200 потоков одновременно отправляют `POST /orders` с товаром X, у каждого свой Idempotency-Key.
- Expected result: ровно один ответ `201`, 199 ответов `409 OUT_OF_STOCK`, ни одного `5xx`. В базе один заказ, `reserved = 1`.
- Evidence: число ответов по каждому коду, результат SQL-проверки ниже.

**CONC-02. Один и тот же запрос много раз**

- Дано: товара достаточно.
- Шаги: 50 потоков одновременно отправляют одинаковый `POST /orders` с одним ключом K.
- Expected result: все ответы `201` с одним и тем же `orderId`. В базе один заказ и один платёж. Заглушка PSP получила один запрос на создание платежа.
- Evidence: коды ответов, число строк в `orders` и `payments`, журнал заглушки PSP.

**CONC-03. Два назначения одновременно**

- Дано: заказ `PAID`, курьеру К1 отправлен оффер, на смене есть свободный курьер К2.
- Шаги: одновременно К1 принимает оффер, а диспетчер вручную назначает на заказ К2.
- Expected result: выполняется одно действие, второе получает `409 ALREADY_ASSIGNED`. У заказа ровно одно активное назначение.
- Evidence: коды ответов, выборка из `assignments` по заказу.

SQL-проверка после каждого конкурентного теста. Все три запроса должны вернуть 0 строк:

```sql
-- резерв больше остатка
SELECT * FROM stock WHERE reserved > on_hand OR reserved < 0;

-- резерв не совпадает с суммой позиций в несобранных заказах
SELECT s.sku_id, s.reserved, COALESCE(r.qty, 0) AS expected
  FROM stock s
  LEFT JOIN (
        SELECT o.darkstore_id, i.sku_id, SUM(i.qty) AS qty
          FROM orders o JOIN order_items i ON i.order_id = o.id
         WHERE o.status IN ('AWAITING_PAYMENT', 'PAID', 'PICKING')
         GROUP BY o.darkstore_id, i.sku_id
       ) r ON r.darkstore_id = s.darkstore_id AND r.sku_id = s.sku_id
 WHERE s.reserved <> COALESCE(r.qty, 0);

-- у заказа больше одного активного назначения
SELECT order_id FROM assignments
 WHERE status IN ('OFFERED', 'ACCEPTED') GROUP BY order_id HAVING COUNT(*) > 1;
```

Второй запрос полезнее первого: он находит резерв, который не сняли после отмены.

## 6. Evidence

Тест без сохранённого результата не считается пройденным. Что прикладывается:

| Тип теста | Что считается доказательством | Где хранится |
|---|---|---|
| Интеграционный, конкурентный | Отчёт прогона в CI с номером сборки, для конкурентных — вывод SQL-проверки | Артефакты сборки |
| Сквозной | История статусов заказа, журнал тестового PSP | Артефакты релиза |
| Нагрузочный | Отчёт Gatling, снимки дашбордов с отметками времени, версия сборки | Артефакты релиза |

В отчёте каждого теста стоит его ID. По матрице из раздела 2 от теста можно дойти до требования и до ADR. Например, если изменится контракт `POST /orders`, видно, что надо пересмотреть FR-03, IT-03, IT-04 и конкурентные тесты.
