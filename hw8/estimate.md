# MediBook: оценка пяти компонентов

Версия: v1, 01.10.2026. Разбивка по задачам — в [wbs.xlsx](wbs.xlsx), сделана по шаблону из лекции.

## Как оценивал

Сначала каждому компоненту дал размер по T-shirt — по шкале из лекции. Потом расписал компонент на задачи в часах и сложил. Так размер S/M/L/XL можно проверить числом.

В лекции у размеров нет чисел, поэтому в днях шкалу задал сам:

| Размер | Что значит (из лекции) | Дней |
|---|---|---|
| S | Понятная задача, минимум неопределённостей | до 10 |
| M | Стандартная сложность, известные паттерны | 11–25 |
| L | Высокая сложность или много интеграций | 26–50 |
| XL | Высокая неопределённость, нужен spike | больше 50 |

Допущения:

- команда: архитектор (частично), 2 backend-разработчика, 1 QA;
- 1 день = 8 часов;
- стек: Java, Spring Boot, PostgreSQL, Redis, RabbitMQ;
- задача готова, когда есть код, тесты и выкладка на staging;
- UI и инфраструктура в оценку не входят.

Auth / Roles из списка в лекции я не оценивал. MediBook подключается к готовому Auth Provider, и объём работы зависит от того, какой он у клиники. Пока это неизвестно, возможна только ROM-оценка: размер M.

## Компоненты

### BFF — S, 9 дней

| Задача | Часы |
|---|---|
| Маршруты и сборка ответов, 10 маршрутов | 28 |
| Проверка JWT и ролей, единый формат ошибок | 20 |
| Таймауты и rate limit | 12 |
| API-тесты | 12 |
| **Всего** | **72** |

Своей базы нет, внешних интеграций нет, логика — принять запрос и собрать ответ из двух сервисов. Неопределённость одна: экраны UI ещё не утверждены, маршрутов может стать больше.

### Appointment Service — L, 32 дня

| Задача | Часы |
|---|---|
| Модель данных и миграции | 16 |
| `POST /appointments`: проверка слота, запись одной транзакцией | 40 |
| Idempotency key | 24 |
| Статусы записи, отмена | 32 |
| Outbox и публикация событий | 32 |
| Чтение: записи пациента, расписание врача | 20 |
| Пациент видит только свои записи | 16 |
| Конкурентный тест: 50 запросов на один слот, 2 прогона по 16 ч | 32 |
| Интеграционные тесты | 32 |
| Логи и метрики | 12 |
| **Всего** | **256** |

Самое дорогое здесь — NFR-02, «нет двойной записи». Резервирование, idempotency key и конкурентный тест вместе дают 96 часов, это больше трети компонента. Паттерны при этом известные, исследовать нечего, поэтому L, а не XL.

### Schedule Service — XL, 53 дня, нужен spike

| Задача | Часы |
|---|---|
| Spike: разобраться с External Schedule API | 40 |
| Модель слотов, CRUD слотов для администратора | 64 |
| Поиск свободных слотов: чтение с реплики, индексы | 32 |
| Redis-кэш слотов и его сброс | 40 |
| Адаптер External Schedule API | 64 |
| Синхронизация расписания и сверка | 48 |
| Работа, когда внешний API недоступен | 24 |
| Проверка слота для Appointment Service | 16 |
| Нагрузочный тест поиска на 1000 RPS, 2 прогона по 20 ч | 40 |
| Интеграционные тесты с заглушкой внешнего API | 40 |
| Логи и метрики | 16 |
| **Всего** | **424** |

Это самый дорогой компонент и компонент с наибольшей неопределённостью. 176 часов из 424 (spike, адаптер, синхронизация, работа без внешнего API) зависят от системы клиники, с которой команда ещё не работала. Нет ни документации, ни тестового доступа. Неизвестно, как клиника сообщает об изменениях расписания и какие у API лимиты.

Поэтому сначала spike на 5 дней: получить доступ, сделать реальные вызовы, понять модель данных. После него оценку адаптера и синхронизации надо пересчитать. До spike 53 дня — предварительная оценка, а не обязательство.

| Задача | Часы |
|---|---|
| Чтение событий из очереди, защита от дублей | 20 |
| Шаблоны уведомлений | 12 |

| Тесты с заглушкой провайдера | 24 |

Чтение очереди, повторы и DLQ — стандартные приёмы. Неопределённость: провайдер SMS не выбран, его лимиты неизвестны.

### Audit Service — M, 19 дней

| Задача | Часы |
|---|---|
| Модель события и API записи | 16 |
| Хранилище только на добавление | 32 |
| Запись аудита в одной транзакции с операцией администратора | 24 |
| Приём событий из очереди | 16 |
| API чтения журнала | 20 |
| Хранение по месяцам | 12 |
| Тест: все операции администратора попадают в журнал | 24 |
| Метрики | 8 |
| **Всего** | **152** |

Внешних интеграций нет. Основная стоимость — требование, чтобы журнал нельзя было изменить (NFR-04). Не согласовано с клиникой: сколько хранить журнал.

## Итог

| Компонент | Размер | Часы | Дни | Spike |
|---|---|---|---|---|
| BFF | S | 72 | 9 | нет |
| Appointment Service | L | 256 | 32 | нет |
| Schedule Service | XL | 424 | 53 | да, 5 дней |
| Notification Worker | M | 128 | 16 | нет |
| Audit Service | M | 152 | 19 | нет |
| **Всего** | | **1 032** | **129** | |

К базовой оценке добавляю запас на риски. Считаю его как в шаблоне: для каждого риска из [risks.md](risks.md) — сколько часов уйдёт на переделку, если он сработает, умножить на вероятность. Вероятность беру как середину диапазона из шкалы рисков: балл 3 — это 30–50%, то есть 40%; балл 4 — 50–70%, то есть 60%.

| Риск | Переделка, ч | Вероятность | Запас, ч |
|---|---|---|---|
| R-01. Внешний API работает не по документации | 160 | 60% | 96 |
| R-02. Конкурентный тест находит двойную запись | 40 | 40% | 16 |
| R-03. Меняется ролевая модель | 80 | 40% | 32 |
| R-04. Поиск не укладывается в 2 секунды | 80 | 40% | 32 |
| R-05. SMS-провайдер ограничивает отправку, нужен второй канал | 40 | 60% | 24 |
| **Всего** | | | **200** |

**129 дней работы + 25 дней запаса = 154 дня.** При условной ставке 2 500 ₽ в час это 3 080 000 ₽.

По календарю: у двух разработчиков 788 часов задач и 200 часов запаса. Если считать 32 рабочих часа в неделю на человека, это около 15–16 недель. Spike идёт в первую неделю, тесты QA — параллельно разработке.

## Что видно из оценки

- Schedule Service и Appointment Service — это 85 дней из 129, две трети всей работы.
- Самое дорогое место — интеграция с системой клиники. Лекция предупреждает именно об этом: интеграция с внешней системой почти всегда дороже, чем кажется.
- Если придётся сократить MVP, можно отложить API чтения журнала аудита (20 часов). Конкурентный тест и сверку расписания откладывать нельзя: они закрывают риски R-02 и R-01.
